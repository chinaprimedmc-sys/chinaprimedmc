# 六类旅客内容：SEO、长尾问题与 AI 搜索优化

本次范围为 About 的六个人群入口和对应文章。每页承担人群规划与服务评估，Journal 承担更具体的攻略，Tours 产品页承担确定路线、天数、服务范围与价格依据。

这是一份基于现有内容和旅客问题制定的编辑布局，不是关键词搜索量、难度或排名报告。另有 Search Console 历史表现的部分观察，见 search-performance-priorities-2026-11-12.md；该观察不证明本轮内容已取得效果。54 组问题是选题与内容定位，不表示已经获得这些词的排名。

## 已实施

- 六页独立标题与描述、自引用 canonical、允许索引及完整搜索摘要。移除六页继承的通用 meta keywords；Google 不使用该标签作为网页排名因素。
- 六段可见概述和 24 段可独立理解的问答；具体问题自然出现在 H3 和正文，不进行关键词堆叠。
- 页面、Article、Breadcrumb 与真实编辑团队实体关联；摘要、问答和来源都对应可见内容。无新增虚构专家、评价、价格、发布日期或核验日期。
- 人群页 → 专题攻略 → 对应产品／服务的内链，相关攻略返回人群页，六页之间按真实需求交叉链接。
- 四篇旧人群文章重新定位为具体服务检查或规划简报，收窄标题与查询定位，保留各自 URL 和 canonical。
- llms.txt 和 llms-full.txt 从同一内容源引用可见概述和问答，作为补充发现入口。这不是 Google AI Overview 的收录条件。
- 保留纯白页面和原有 HubSpot 咨询流程；目录在较矮桌面窗口内可滚动，手机端保持普通文档流。

## 判断效果的方法

上线后在 Google Search Console 检查六个 canonical 的抓取与索引状态，再按页面观察查询、曝光、点击率和询盘。根据实际出现的词完善内容；不要仅因短期没有排名新增近似页面。若旧攻略与新入口对同一查询持续交替，结合真实查询和页面价值决定进一步区分或合并，合并时再制定重定向。

### 从文章阅读到有效询盘

- 六页共 12 个咨询按钮沿用现有 `cta_click` 事件，通过 `traveler_guide` 区分人群，通过 `placement=guide-hero` 或 `guide-closing` 区分位置。点击只代表咨询意向。
- 从文章链接直接进入 `/start-planning` 时，保留已有 `source` 参数，并将允许列表中的来源转换为同一 `traveler_guide`。现有 HubSpot 成功提交事件 `generate_lead` 自动取得该上下文；打开表单或点击提交不计作成功询盘。
- About、公司和创始人页面上的事件增加 `brand_page`；创始人现有 `source=founder-story`、About 现有 `source=about-capability` 与 `source=about-service-cases` 的直接咨询路径映射到对应 `brand_page`。仅接受这些公开来源标识。
- 这些事件遵守现有分析同意设置；未同意的访问不产生此分析数据。不将表单正文、邮箱或任意查询参数纳入新增属性，也未改用其他表单服务。
- 当前为页面上下文和文章直接到咨询页的归因；经过其他页面、重新访问或丢失参数时，不推断原文章来源。它不是完整的跨会话、多触点归因。
- 发布后用同意分析的测试会话检查按钮事件和属性，再检查正式 HubSpot 成功事件。需要在 GA4 中注册相应自定义维度，才能方便地按指南和按钮位置生成报表。本次未操作 GA4 管理后台、未发送测试询盘，也未验证线上事件。

建议按六个页面分别观察：Search Console 曝光与点击 → `cta_click` → `generate_lead` → CRM 中的实际有效询盘。搜索表现与分析事件来自不同系统，且受同意选择影响，不将两者直接视为逐人完整漏斗。

AI Overview 的展示和引用由 Google 决定。本次完成的是可抓取内容、直接回答、清晰出处和语义关联，不能据此声称已被引用或保证展示。也不把 FAQPage 标记、llms.txt 或某一种特殊 AI 标记当作展示捷径。
